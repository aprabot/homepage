Context: Product map

The product has five pages and one chatbot. One rule ties them together: committing a scheme or campaign changes the plan that every later forecast uses, while a scenario only tries changes on a copy. Lyra can create or explain on any page. Optimization comes after this foundation.

  • Draft: editable, and ignored by every forecast run.
  • Committed: locked. Every later forecast run treats it as a known input — a scheme as a known price and discount, a campaign as planned spend. Committing starts a background re-run.
  • Withdraw: a committed item stops counting in new runs and its history is kept. To change a committed item, withdraw it and create a new version.
  • Scenario: a copy of the plan. Nothing done in a scenario edits a committed item. Apply to plan turns the scenario changes into drafts for the user to review and commit.

4. One user journey, end to end

  1. Onboard: upload or connect sales, marketing spend, SKU master; weather and festivals are generated. Train the first forecast.
  2. Create schemes in Discount Schemes for the pincodes, dates and SKUs wanted, give each a code, and commit them.
  3. Create campaigns in Marketing Campaigns, commit them, and launch them on Meta or Google.
  4. Each commit triggers a forecast re-run that includes the committed items.
  5. Review SKU and pincode forecasts in Output, with last year beside every metric.
  6. Open Scenarios to try changes: spend up 5%, a holiday off in a pincode, a cap on a pincode. Compare with the plan.
  7. For the final scenario — run the inventory requirement.
  8. If a scenario is liked, Apply to plan creates drafts. The user commits them, and the loop repeats.
  9. At any step, ask Lyra to create a draft, run a scenario, or explain why a forecast is high or low.

5. Where Optimization plugs in

Optimization starts after this foundation and only adds recommendations; it never commits on its own.

  • Scheme ranking appears on the Discount Schemes create page, ranking the schemes the user drafted for a pincode and SKU.
  • Marketing allocation appears in Amplify under AI Opportunities, as recommended spend by pincode, SKU, platform and campaign type.
  • Timing recommendations appear as a calendar of best start weeks.
  • Every recommendation creates a draft. The user can test it in Scenarios and then commit it.
This foundation provides what optimization needs: a scheme registry, campaigns with a scope, committed inputs, scenarios to test recommendations, and Output with last year beside the forecast.

  • Does a missing sales row mean zero sales, or missing data?
  • Can one sales row carry two stacked schemes, or only one scheme_id?
  • Is spend per row the total for that SKU and pincode, or the campaign total across all its rows?
  • Which postal-code dataset and weather provider per country, and which official festival calendar, starting with which countries?

  • How should the interface show a budget change on a live campaign?
  • Which platforms and countries allow targeting by pincode?
  • Which last-year match is the Output default: 364 days back, the same dates, or festival-aligned?
  • How many scenarios can a user save, and how long are scenario runs kept?

4. Principles

  • One topic per step, one file per topic, one template per file, each with an example row in the right country format.
  • The top of each step says whether it is required, optional or automatic, and what the forecast loses when data is missing.
  • Validate on upload and show row-level errors with a downloadable file of the problem rows; never a bare failure.
  • Separate blocking errors (cannot train) from warnings (can train, lower quality).
  • Save progress automatically, so the user can leave and resume at any sub-part.
  • Long work runs in the background with a progress bar, and the user can continue to the next step.
  • Everything is keyed at pincode level: the pincode master is the spine of the data model.

Lyra

Static review mockup — transcribed from the product team's spec. Nothing on this page is wired to real data.

Lyra already explains forecasts. This adds creation by chat for schemes, campaigns and scenarios, and says how the explanation should use the last-year comparison and scenarios. Chat panel on every page.

What Lyra can do

10% off SKU A, pincodes 400001 to 400010, 1 to 15 Dec, code DEC10
Lyra
Drafted scheme DEC10 — 10% off, SKU A, pincodes 400001–400010, 1–15 Dec.
+5% spend on campaign C, and turn Diwali off for pincode 560001
Lyra
Ran it. Revenue +6.2%, units +5.8% vs the base run, 0 capped units.
why is SKU A high in 400001 in November compared with last year?
Lyra
SKU A in 400001 is forecast +18% vs last November. Top drivers: scheme DEC10 is committed for these dates and adds about 180 units; Diwali falls in this week, while last year it fell three weeks later.
These are model attributions, not proof of cause.

Guardrails

  • Drafts and scenarios only. Commit, launch and withdraw need a click by the user.
  • Permissions follow the user's role: a viewer cannot create.
  • Show what was defaulted or assumed.
  • Forecast numbers come from the tools, never from the model's memory.
  • Ask when a SKU, pincode or date is ambiguous.
  • Keep an audit log of what was asked and what Lyra created.
    Done when
  • A scheme draft can be created from a sentence, and commit still needs a click.
  • A campaign draft can be created the same way.
  • A scenario can be created and run from a sentence, with the comparison returned.
  • An explanation lists drivers with direction and size, compares with last year, and states caveats.
  • Every created item shows Lyra as its creator.
